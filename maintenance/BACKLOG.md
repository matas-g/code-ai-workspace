## Why one backlog

A separate bug list would make it easy to implement overlapping skill, template and runtime changes twice or in the wrong order. Keeping the entire technical review as the daily queue would make priorities and progress hard to find. Use this short ordered backlog, with links to the detailed review and evidence. Only this file owns current implementation rank and status.

This choice applies GitHub's guidance on a single source of truth, small reviewable work items and explicit dependencies to the existing Markdown workflow; it does not require adopting GitHub Projects. [GitHub project practices](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/best-practices-for-projects).

## Priority and completion rules

- **P1:** Fix or verify before a wider pilot or the corresponding stronger reliability/platform claim. **P2:** Follow-up quality work after the immediate defects. **P3:** Optional adoption, only when needed. Rank orders eligible work within these boundaries; an independent small fix can proceed while platform access is unavailable.
- Manual test priorities have a different purpose: the tracker's P0 means verify before relying on automatic context. It does not automatically make every pending platform check a confirmed critical defect.
- Dependencies below refer to the needed implementation/checking capability. Native/manual closure is tracked separately in B13/B14 and the release gates. Run each fix's targeted checks immediately; do not defer all manual testing to the end.
- Status values: `Not started`, `In progress`, `Awaiting verification`, `Blocked`, `Complete`, `Deferred`. A blocked item must name its actual missing dependency/environment and next action. Keep progressing on eligible work.
- A fix is complete only when its acceptance criteria, affected documentation and appropriate regression checks are satisfied. An AI behavior or rendering fix remains `Awaiting verification` until the relevant native IDE retest is recorded. Historical PASS results stay scoped to their original release/environment.

## Release gates

1. **Wider pilot:** Relevant P1 defects are fixed, deterministic regression checks pass, and affected native IDE/manual retests have actual evidence. B13/B14 list residual platform/policy/usability limits. An unavailable platform may remain explicitly outside a scoped macOS pilot; it cannot be advertised as validated.
2. **AI workflow claim:** Instruction inclusion and correct fact lookup are separate from ticket-scope compliance, literal prompt capture and recovery messaging. B02/B04/B06 require actual IDE evidence even though existing macOS discovery/loading matrices passed.
3. **Artifact:** Run B12 against the exact release candidate; use the [technical acceptance matrix](QUALITY_IMPROVEMENT_PLAN.md#10-final-acceptance-matrix-for-the-improved-release) for changed areas. Keep this backlog, the technical review, AGENTS.md and MANUAL_TESTS.md outside the release inventory and generated workspaces. Extend exclusion checks accordingly.
4. **Public/open-source release:** B15's applicable owner decisions and publication review are complete. P2 work is not an automatic pilot blocker; record deferrals and remaining limitations explicitly.

## Keeping this useful

- Add new work here with a stable B ID, evidence/type, priority, dependencies and a verifiable completion gate. Reuse an existing item when the same change resolves both a defect and an improvement. Rank may change; IDs must not.
- Record implementation status, update date, decisions and PR/evidence links in the owning row. For a partly finished package, name the remaining subtask; do not mark the whole package complete after only its small wording change.
- Keep detailed design/acceptance reasoning in the technical review and actual tester observations in MANUAL_TESTS.md. A new result updates the current status while preserving earlier evidence. Do not reset unrelated passed checks or infer a pass from file presence/automation.
- When a change affects more than one item, update every affected dependency/gate. A verified macOS fix with Windows pending remains explicit about that boundary.
- Use synthetic fixtures; put transient work under `_tmp/`. Reusable verification recipes belong in tracked maintainer files under B01/B12/B17, since another contributor cannot access ignored evidence.
- During an actual release, edit the product version only at `VERSION` in workspace_manager.py; prepare the user README label/manifest hashes with `build_release.py`, build versioned names using `--output-dir`, and archive the superseded ZIP/checksum under `_old zips/` without overwriting old archives. Record changelog and real test evidence explicitly. User-only packaging is tracked in B21; test archives stay under `_tmp/` until an actual release is requested.
